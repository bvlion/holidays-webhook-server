# 秘密情報の管理

## 1. 目的と対象

この文書は、Issue #209 に基づき、2026-08-03 時点の秘密情報、個人情報、ログ、GitHub Actions設定の管理方法を定める。

対象は次のとおりである。

- ローカルおよび本番の環境変数
- Google認証情報とGoogle Calendar APIキー
- GitHub ActionsのSecretsおよびVariables
- SSH秘密鍵とSlack Webhook URL
- アプリケーション、Webサーバー、データベースのログ
- Git履歴に残る過去の設定ファイル

## 2. 基本方針

- 実値を含む `.env`、秘密鍵、認証JSON、トークンをGitへ追加しない。
- 新規開発者と継続的インテグレーションは、公開用 `.env.example` から `src/.env` を作成する。
- `.env.example` の `APP_KEY` とデータベース認証情報はローカル・テスト専用の公開値とし、本番で再利用しない。
- 秘密情報をIssue、Pull Request、Slack、ログ、コマンド出力、テスト結果、コミットメッセージへ貼り付けない。
- ログへAuthorizationヘッダー、Cookie、URLクエリ、リクエスト本文、外部レスポンスの実値を出力しない。
- 漏洩が疑われる値は、Gitからの削除だけで安全になったと判断せず、提供元で失効・再発行する。

## 3. 環境別の配置

### 3.1 ローカル開発とテスト

`make setup` では、`src/.env` が存在しない場合だけ次のファイルを作る。再実行時に既存の `src/.env` は上書きしない。

```text
.env.example -> src/.env
```

`src/.env` はGit管理外である。Google連携を使用しない通常の起動とテストでは、Google関連の値を空のまま使用できる。

ローカル開発用Make targetは、アプリケーション起動またはデータベースアクセスの前に、接続設定が `.env.example` のローカル固定値と一致し、`DATABASE_URL`が存在しないことを検査する。検査失敗時は、データベースパスワードを含む設定値を出力せずに停止する。検査通過後は、古い接続先を含み得るLaravel設定キャッシュを削除する。

Google連携が必要な場合は、管理者から安全な経路で受け取った `lib/google_client_secret` を配置し、`lib/google_client_export.php` で `src/.env` へ反映する。`lib/google_client_secret` もGit管理外である。

### 3.2 継続的インテグレーション

Pull Request用ワークフローは `.env.example` を `src/.env` へコピーする。現在のテストはGoogle、Slack、SSHの秘密情報を必要としない。Dependabotを含めて標準の `pull_request` イベントでテストし、Pull RequestのコードをSecretへアクセスできる `pull_request_target` では実行しない。テストjobの権限はリポジトリ内容の読み取りだけとする。

Slack通知は `SLACK_WEBHOOK_URL` をGitHub Actions Secretから受け取り、mainへのpushだけで実行する。テストレポートの公開もmainへのpushだけで行い、公開jobだけにリポジトリ内容の書き込み権限を与える。Pull Requestでは、秘密情報と書き込み権限を使用せずテストだけを実行する。

### 3.3 本番

本番の `.env` はXServerの配備先に置き、GitHub Actionsのrsync対象から除外する。現在のデプロイはサーバー上の既存 `.env` を保持する。

本番 `.env` では、少なくとも次を実値で管理する。

- `APP_KEY`
- `DB_HOST`、`DB_DATABASE`、`DB_USERNAME`、`DB_PASSWORD`
- `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`
- `GOOGLE_CALENDAR_API_KEY`
- `GOOGLE_CALLBACK_URL`

ファイルはアプリケーション実行ユーザーだけが読める所有者・権限にし、バックアップにも本番データと同じアクセス制御を適用する。更新後はLaravelの設定キャッシュに古い値が残っていないことを確認する。

本番 `APP_KEY` がGit履歴上の公開済みキーと一致するかどうかの照合手順は7章を参照する。

## 4. GitHub Actionsの管理項目

2026-08-03 時点で、リポジトリにはActions Variableがなく、次の項目がActions Secretとして登録されている。

| 名前 | 分類 | 現在の用途 |
| --- | --- | --- |
| `ID_RSA` | Secret | 本番配備用SSH秘密鍵 |
| `SLACK_WEBHOOK_URL` | Secret | テスト・デプロイ結果通知 |
| `KNOWN_HOSTS` | 接続先の完全性情報 | SSH接続先の検証 |
| `SSH_HOST` | 環境設定 | 配備先ホスト |
| `SSH_PORT` | 環境設定 | SSHポート |
| `SSH_USER` | 環境設定 | SSHユーザー |
| `SSH_DIR` | 環境設定 | 配備先ディレクトリ |

`ID_RSA` と `SLACK_WEBHOOK_URL` はSecretとして維持する。`KNOWN_HOSTS` と `SSH_*` は値の公開可否を運用者が確認したうえで、Actions Variableへの移行候補とする。現在はVariableが未登録であるため、このIssueではワークフローの参照先を変更しない。

代表的に移行が失敗するのは、Secret参照だけをVariable参照へ変更し、同名のVariableが未登録の状態でデプロイする場合である。最小ガードとして、Variableの登録確認後にワークフローを変更し、手動の接続確認を行う。

GitHubが自動発行する `GITHUB_TOKEN` はActions外へ保存しない。

## 5. ログと保存データ

### 5.1 アプリケーションログ

アプリケーションが明示的に記録している祝日キャッシュのログは、キャッシュファイルのパスと国・年のキーだけであり、APIキーや取得URLを記録しない。

例外処理に秘密情報を追加で記録する処理はない。今後ログを追加する場合も、コマンドのヘッダー、パラメーター、Google認証コールバックのクエリを記録しない。

### 5.2 Apacheアクセスログ

Google認証コールバックのURLクエリには、一時的な認証コードが含まれ得る。ローカルApacheは `%U` を使用したクエリなしのログ形式とし、リクエスト行全体を記録しない。

本番公開経路はXServerのnginxであり、設定はリポジトリ外にある。本番アクセスログがクエリ文字列を記録していないか、運用者による確認が必要である。

### 5.3 MySQLログ

コマンドのヘッダーやパラメーターには、外部サービスの認証情報が含まれ得る。SQLの値をそのまま記録するgeneral logはローカル設定で無効化する。

### 5.4 外部HTTPレスポンス

時間トリガーは、外部HTTPレスポンスのヘッダーと本文を `exec_results` に保存する。手動実行は同じ情報をAPIレスポンスとして返す。これはログではないが、外部サービスの機密値が含まれる可能性がある。

現在は保存前のマスキング処理がないため、外部HTTP実行先の応答内容、データベースへのアクセス権、保存期間を後続Issueで確認する。代表的に問題になるのは、外部サービスがレスポンスヘッダーへ再利用可能なトークンを含める場合である。最小ガードとして、そのような実行先を登録せず、必要な場合は保存前の項目別マスキングを実装する。

## 6. 監査結果

### 6.1 現行ツリー

- 追跡対象だったルート `.env` には、実値形式の `APP_KEY` が含まれていたため削除した。
- 同ファイルのGoogle関連値とデータベースパスワードはプレースホルダー形式であり、実値形式のGoogle認証情報は確認されなかった。
- `.env.example` はローカル・テスト専用の公開値と空のGoogle設定だけを持つ。
- 秘密鍵、認証JSON、Slack Webhook URL、Google APIキーの実値は現行ツリーから検出されなかった。

### 6.2 Git履歴

値を完全にマスクしたGitleaksで、監査開始時点のmainまでの602コミットを走査し、組み込みルールに一致する漏洩は検出されなかった。

GitleaksがLaravelの `APP_KEY` を検出対象にしないため、`.env`、`src/.env`、`src/.env.testing` を別途確認した。その結果、2種類の実値形式の `APP_KEY` がGit履歴に残っている。現在のツリーからファイルを削除しても、過去コミットから値を取得できる状態は変わらない。

履歴の一括書き換えは、既存clone、未完了ブランチ、コミット参照を無効化する破壊的な操作になるため、このIssueでは実施しない。代表的に問題になるのは、書き換え前のブランチを再度pushして秘密情報を履歴へ戻す場合である。最小ガードとして、失効を先に完了し、関係者と停止時間を調整してから全参照を対象に書き換える。

## 7. 人間による本番 `APP_KEY` 照合と秘密情報確認チェックリスト

### 7.1 照合の目的

Git履歴には2種類の実値形式の `APP_KEY` が残っており、これらは公開リポジトリの履歴から取得できるため、すでに公開済みの秘密情報として扱う。一方で、本番XServerが現在使用している `APP_KEY` がこの2種類のどちらかと同一かどうかはまだ確認されていない。

この照合の目的は、

**Git履歴上で公開されてしまった `APP_KEY` が、現在も本番環境で使用され続けているかを判定すること**

である。判定結果によって、後続で何を行うかが変わる。

- `MATCH`(本番キーが履歴上の2種類のいずれかと一致): 現在有効な本番キーも公開済みとして扱う必要がある。ただし `APP_KEY` の変更は、既存セッション、Cookie、Laravelで暗号化した保存値を復号できなくする副作用があるため、確認なしに即座には変更せず、7.6のチェックリストに従って影響を確認したうえでローテーションを検討する。
- `NO_MATCH`(本番キーが履歴上の2種類のどちらとも異なる): 少なくとも今回確認されたGit履歴上の漏洩によって、現在の本番 `APP_KEY` が公開されている状態ではない。したがって、今回の監査だけを理由とした `APP_KEY` のローテーションは不要である。

つまりこの照合は、**現在の本番キーが実際に漏洩対象なのかを確認し、必要な場合だけ安全にローテーションするため**に行う。

### 7.2 本番配備の前提

`.github/workflows/deploy.yaml` はXServer上で `git pull` するデプロイではない。GitHub Actions runner上でリポジトリをcheckoutし、`src/` の内容をrsyncでXServerへ転送し、`.env` はrsync対象から除外してXServer上の既存ファイルを保持する構成である。

したがって、**XServerの本番配備先にGit履歴が存在する前提を置いてはならない**。Git履歴の検索や比較をXServer上で行う手順は不適切であり、実施しない。

この前提から、照合処理は次の2環境へ明確に分離する。

- XServer: 本番 `.env` の現在の `APP_KEY` を読み取り、その場でSHA-256へ変換するところまでを行う。実値をXServer外へ持ち出さない。
- 信頼できるローカルclone: Git履歴上の実値形式 `APP_KEY` を確認し、その場でSHA-256へ変換して本番側のハッシュと比較する。Git履歴の検索・比較はここでのみ行う。

2環境へ分離するのは、本番 `APP_KEY` の実値をXServer外(ローカルPCや通信経路)へ一切持ち出さず、比較可能なSHA-256ハッシュだけをXServerの外へ出すためである。ハッシュ自体から元の `APP_KEY` を復元することは事実上できないため、この分離によって実値の露出範囲をXServer上の1コマンドの実行時だけに限定できる。

### 7.3 XServer側の手順(SHA-256取得のみ)

XServerで行うのは、**現在の本番 `APP_KEY` のSHA-256取得まで**である。Git履歴の検索や比較はXServerでは行わない。

要件:

- `APP_KEY` の実値を標準出力へ出さない
- `APP_KEY` の実値をローカルPCへコピーしない
- `APP_KEY` の実値をコマンドライン引数へ埋め込まない
- `APP_KEY` の実値をshell historyへ残さない
- `APP_KEY` の実値を一時ファイルへ保存しない
- 照合用スクリプトや一時スクリプトをXServerへ保存しない(特に共有 `/tmp` へ置かない)
- `/tmp` 等へファイルを書き込まない
- `APP_KEY` が存在しない、空、想定形式外、複数定義で解釈が曖昧、のいずれの場合もSHA-256を出力せずエラー終了する
- 正常時に出力するのは64文字のSHA-256のみとする

手順:

1. 普段運用で使っている接続方法で、本番XServerへSSH接続する。接続先ホスト・ポート・ユーザーはGitHub Actions Secretの `SSH_HOST`・`SSH_PORT`・`SSH_USER` に対応する値だが、これらのSecret名がローカルshellの環境変数として自動的に定義されているわけではない。運用者が把握している実際の接続情報を用いる。
2. 本番配備ディレクトリ(Actions Secretの `SSH_DIR` に対応するディレクトリ)へ `cd` する。
3. 接続したシェル上で、次のPHPコマンドをそのまま実行する。`.env` から `APP_KEY=` 行を安全に取得し、定義が存在しない場合・ちょうど1件でない場合・値が空または想定するLaravelの `base64:` 形式(32byteをbase64化した43文字+パディング1文字)に一致しない場合はエラー終了し、正常時だけ64桁のSHA-256を1行出力する。

```shell
php -r '
$lines = file(".env", FILE_IGNORE_NEW_LINES);
$matches = [];
foreach ($lines as $line) {
    if (strncmp($line, "APP_KEY=", 8) === 0) {
        $matches[] = trim(substr($line, 8), " \t\r\n\"\x27");
    }
}
if (count($matches) !== 1) {
    fwrite(STDERR, "APP_KEY is missing or defined more than once\n");
    exit(1);
}
$value = $matches[0];
if ($value === "" || !preg_match("/^base64:[A-Za-z0-9+\/]{43}=$/", $value)) {
    fwrite(STDERR, "APP_KEY is empty or not in the expected format\n");
    exit(1);
}
echo hash("sha256", $value), PHP_EOL;
'
```

表示された64桁16進のSHA-256だけを控え、7.4のローカル照合スクリプトへ渡す。`APP_KEY=` の行内容(実値)自体は、このPHPコードにも標準出力にも一切含まれない。

### 7.4 ローカルclone側の手順(Git履歴との照合)

Git履歴を保持する信頼できるローカルcloneで、`.env`・`src/.env`・`src/.env.testing` のGit履歴を対象に、実値形式の `APP_KEY` を確認する。目的は、**Git履歴上の公開済み `APP_KEY` を実値のまま表示・保存せず、SHA-256へ変換して本番側のハッシュと比較すること**である。

この作業には `scripts/check-app-key-history.sh` を使う。要件:

- Gitリポジトリ内でのみ動作し、Gitリポジトリでなければエラー終了する
- XServerでは実行しない(ローカル専用)
- 本番 `APP_KEY` のSHA-256のみを非表示入力で受け取り、64文字のSHA-256形式であることを検証する
- Git履歴上の `APP_KEY` 実値を標準出力や一時ファイルへ一切出さない。比較のために一時保存するのはSHA-256ハッシュだけであり、使用する一時ファイルはスクリプト終了時に必ず削除する
- ユニークな実値形式の履歴上 `APP_KEY` が2種類であることを確認する。2種類でなければ安全側に倒してエラー終了する
- 最終的な標準出力は `MATCH` または `NO_MATCH` のみとする

実行例:

```shell
scripts/check-app-key-history.sh
本番 APP_KEY の SHA-256 (64桁16進)を入力してください: ********************************************************
MATCH
```

### 7.5 照合結果の記録

本番キー、Git履歴上のキー、SHA-256値のいずれも、Issue、Pull Request、ログ、コミットメッセージへ記録しない。Issue #209へ記録するのは `MATCH` または `NO_MATCH` という照合結果だけとする。

### 7.6 APP_KEY固有のチェックリスト(`MATCH` の場合のみ)

以下は、7.1〜7.4の照合結果が `MATCH` だった場合にだけ実施する、`APP_KEY` 固有のチェックリストである。`NO_MATCH` の場合、今回の漏洩を理由とした本チェックリストの実施は不要である。

- [ ] 保守時間を確保して新しい `APP_KEY` を生成し、本番 `.env` を更新する
- [ ] `APP_KEY` 変更により、既存セッション、Cookie、Laravelで暗号化した保存値が復号できなくなる影響を確認する
- [ ] 設定キャッシュを再生成し、ログイン、Googleコールバック、主要APIを確認する
- [ ] 旧 `APP_KEY` をバックアップ、ログ、共有メモから削除する

### 7.7 Issue #209全体に対する秘密情報確認(`MATCH` / `NO_MATCH` に依存しない)

以下は、本番 `APP_KEY` の照合結果が `MATCH` か `NO_MATCH` かに関わらず必要な確認である。Issue #209はAPP_KEYだけでなく、Google認証情報、GitHub Actions Secrets、Slack Webhook URL、SSH秘密鍵、認証JSON等を監査対象としており、これらの確認要否は今回のAPP_KEY照合結果に左右されない。

- [ ] Google Cloud Consoleで、リポジトリのプレースホルダー以外に漏洩したOAuthクライアントシークレットまたはAPIキーがないことを確認する
- [ ] 漏洩が確認されたGoogle認証情報がある場合は失効・再発行し、本番 `.env` を更新する
- [ ] GitHub Actionsの `ID_RSA` と `SLACK_WEBHOOK_URL` がIssue、ログ、外部共有先へ露出していないことを確認する
- [ ] 露出が確認されたActions Secretは提供元で失効・再発行し、GitHubの登録値を更新する
- [ ] 必要な場合は、関係者とGit履歴書き換えおよび全cloneの再取得手順を調整する

Git履歴の一括書き換え自体は、既存clone、未完了ブランチ、コミット参照を無効化する破壊的な操作であるため、実施する場合は失効を先に完了し、関係者と停止時間を調整してから全参照を対象に行う。

## 8. Issue #209を閉じる条件

Issue #209は、このPull Requestのマージだけでは閉じない。運用者が7.1〜7.4の手順で本番XServerの `APP_KEY` とGit履歴上の2種類を安全な環境で照合し、値を一切記録せず、`MATCH` または `NO_MATCH` という照合結果だけをIssue #209で確認できる状態になってから、次のいずれかに従って閉じる。

いずれの場合も、7.7に挙げたAPP_KEY以外の秘密情報確認(Google認証情報、GitHub Actions Secrets等)は、今回のAPP_KEY照合結果に関わらず別途完了させる必要がある。これらはAPP_KEYの `MATCH` / `NO_MATCH` によって要否が変わるものではない。

### `NO_MATCH` の場合

現在の本番キーは、今回確認されたGit履歴上の公開済みキーとは異なる。

- 照合結果 `NO_MATCH` のみをIssue #209で確認できる状態にする
- 今回の漏洩を理由とした `APP_KEY` 変更(7.6)は不要である
- 7.7の確認と他の完了条件に問題がなければ、Issue #209はclose可能である

### `MATCH` の場合

現在の本番キーが公開済みキーと同一である。

- 照合結果 `MATCH` のみをIssue #209で確認できる状態にする
- Issue #209はその場では即closeしない
- 7.6のAPP_KEY固有チェックリストに従って影響確認へ進む
- 本番キー変更の必要性と実施手順は、照合結果に基づいて運用者が別途判断する

いずれの場合も、本番キーの変更、影響確認、秘密情報の失効・再発行、Git履歴の書き換えは、このPull Requestの対象外とする。

## 9. 確認手順

秘密情報を検索する際は、必ず検出値を完全にマスクする。検索結果にはファイル名、コミット、キー名だけを残し、値を標準出力やレポートへ含めない。

Pull Requestでは次を確認する。

1. `.env`、秘密鍵、認証JSONが追跡対象に追加されていないこと
2. `.env.example` に本番値が含まれていないこと
3. Git差分に秘密情報形式の値がないこと
4. ローカル・テスト用設定だけでアプリケーションテストを実行できること
5. ApacheアクセスログにURLクエリが記録されないこと
6. MySQL general logが無効であること
