# 秘密情報の管理

## 1. 目的と対象

この文書は、Issue #209 に基づき、2026-08-03 時点の秘密情報、個人情報、ログ、GitHub Actions設定の管理方法を定める。

対象は次のとおりである。

- ローカルおよび本番の環境変数
- Google認証情報とGoogle Calendar APIキー
- GitHub ActionsのSecretsおよびVariables
- SSH秘密鍵とSlack Webhook URL
- アプリケーション、Webサーバー、データベースのログ
- Git履歴に残る過去の設定ファイル

## 2. 基本方針

- 実値を含む `.env`、秘密鍵、認証JSON、トークンをGitへ追加しない。
- 新規開発者と継続的インテグレーションは、公開用 `.env.example` から `src/.env` を作成する。
- `.env.example` の `APP_KEY` とデータベース認証情報はローカル・テスト専用の公開値とし、本番で再利用しない。
- 秘密情報をIssue、Pull Request、Slack、ログ、コマンド出力、テスト結果、コミットメッセージへ貼り付けない。
- ログへAuthorizationヘッダー、Cookie、URLクエリ、リクエスト本文、外部レスポンスの実値を出力しない。
- 漏洩が疑われる値は、Gitからの削除だけで安全になったと判断せず、提供元で失効・再発行する。

## 3. 環境別の配置

### 3.1 ローカル開発とテスト

セットアップでは次のファイルを作る。

```text
.env.example -> src/.env
```

`src/.env` はGit管理外である。Google連携を使用しない通常の起動とテストでは、Google関連の値を空のまま使用できる。

Google連携が必要な場合は、管理者から安全な経路で受け取った `lib/google_client_secret` を配置し、`lib/google_client_export.php` で `src/.env` へ反映する。`lib/google_client_secret` もGit管理外である。

### 3.2 継続的インテグレーション

Pull Request用ワークフローは `.env.example` を `src/.env` へコピーする。現在のテストはGoogle、Slack、SSHの秘密情報を必要としない。Dependabotを含めて標準の `pull_request` イベントでテストし、Pull RequestのコードをSecretへアクセスできる `pull_request_target` では実行しない。テストjobの権限はリポジトリ内容の読み取りだけとする。

Slack通知は `SLACK_WEBHOOK_URL` をGitHub Actions Secretから受け取り、mainへのpushだけで実行する。テストレポートの公開もmainへのpushだけで行い、公開jobだけにリポジトリ内容の書き込み権限を与える。Pull Requestでは、秘密情報と書き込み権限を使用せずテストだけを実行する。

### 3.3 本番

本番の `.env` はXServerの配備先に置き、GitHub Actionsのrsync対象から除外する。現在のデプロイはサーバー上の既存 `.env` を保持する。

本番 `.env` では、少なくとも次を実値で管理する。

- `APP_KEY`
- `DB_HOST`、`DB_DATABASE`、`DB_USERNAME`、`DB_PASSWORD`
- `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`
- `GOOGLE_CALENDAR_API_KEY`
- `GOOGLE_CALLBACK_URL`

ファイルはアプリケーション実行ユーザーだけが読める所有者・権限にし、バックアップにも本番データと同じアクセス制御を適用する。更新後はLaravelの設定キャッシュに古い値が残っていないことを確認する。

## 4. GitHub Actionsの管理項目

2026-08-03 時点で、リポジトリにはActions Variableがなく、次の項目がActions Secretとして登録されている。

| 名前 | 分類 | 現在の用途 |
| --- | --- | --- |
| `ID_RSA` | Secret | 本番配備用SSH秘密鍵 |
| `SLACK_WEBHOOK_URL` | Secret | テスト・デプロイ結果通知 |
| `KNOWN_HOSTS` | 接続先の完全性情報 | SSH接続先の検証 |
| `SSH_HOST` | 環境設定 | 配備先ホスト |
| `SSH_PORT` | 環境設定 | SSHポート |
| `SSH_USER` | 環境設定 | SSHユーザー |
| `SSH_DIR` | 環境設定 | 配備先ディレクトリ |

`ID_RSA` と `SLACK_WEBHOOK_URL` はSecretとして維持する。`KNOWN_HOSTS` と `SSH_*` は値の公開可否を運用者が確認したうえで、Actions Variableへの移行候補とする。現在はVariableが未登録であるため、このIssueではワークフローの参照先を変更しない。

代表的に移行が失敗するのは、Secret参照だけをVariable参照へ変更し、同名のVariableが未登録の状態でデプロイする場合である。最小ガードとして、Variableの登録確認後にワークフローを変更し、手動の接続確認を行う。

GitHubが自動発行する `GITHUB_TOKEN` はActions外へ保存しない。

## 5. ログと保存データ

### 5.1 アプリケーションログ

アプリケーションが明示的に記録している祝日キャッシュのログは、キャッシュファイルのパスと国・年のキーだけであり、APIキーや取得URLを記録しない。

例外処理に秘密情報を追加で記録する処理はない。今後ログを追加する場合も、コマンドのヘッダー、パラメーター、Google認証コールバックのクエリを記録しない。

### 5.2 Apacheアクセスログ

Google認証コールバックのURLクエリには、一時的な認証コードが含まれ得る。ローカルApacheは `%U` を使用したクエリなしのログ形式とし、リクエスト行全体を記録しない。

本番公開経路はXServerのnginxであり、設定はリポジトリ外にある。本番アクセスログがクエリ文字列を記録していないか、運用者による確認が必要である。

### 5.3 MySQLログ

コマンドのヘッダーやパラメーターには、外部サービスの認証情報が含まれ得る。SQLの値をそのまま記録するgeneral logはローカル設定で無効化する。

### 5.4 外部HTTPレスポンス

時間トリガーは、外部HTTPレスポンスのヘッダーと本文を `exec_results` に保存する。手動実行は同じ情報をAPIレスポンスとして返す。これはログではないが、外部サービスの機密値が含まれる可能性がある。

現在は保存前のマスキング処理がないため、外部HTTP実行先の応答内容、データベースへのアクセス権、保存期間を後続Issueで確認する。代表的に問題になるのは、外部サービスがレスポンスヘッダーへ再利用可能なトークンを含める場合である。最小ガードとして、そのような実行先を登録せず、必要な場合は保存前の項目別マスキングを実装する。

## 6. 監査結果

### 6.1 現行ツリー

- 追跡対象だったルート `.env` には、実値形式の `APP_KEY` が含まれていたため削除した。
- 同ファイルのGoogle関連値とデータベースパスワードはプレースホルダー形式であり、実値形式のGoogle認証情報は確認されなかった。
- `.env.example` はローカル・テスト専用の公開値と空のGoogle設定だけを持つ。
- 秘密鍵、認証JSON、Slack Webhook URL、Google APIキーの実値は現行ツリーから検出されなかった。

### 6.2 Git履歴

値を完全にマスクしたGitleaksで、監査開始時点のmainまでの602コミットを走査し、組み込みルールに一致する漏洩は検出されなかった。

GitleaksがLaravelの `APP_KEY` を検出対象にしないため、`.env`、`src/.env`、`src/.env.testing` を別途確認した。その結果、2種類の実値形式の `APP_KEY` がGit履歴に残っている。現在のツリーからファイルを削除しても、過去コミットから値を取得できる状態は変わらない。

履歴の一括書き換えは、既存clone、未完了ブランチ、コミット参照を無効化する破壊的な操作になるため、このIssueでは実施しない。代表的に問題になるのは、書き換え前のブランチを再度pushして秘密情報を履歴へ戻す場合である。最小ガードとして、失効を先に完了し、関係者と停止時間を調整してから全参照を対象に書き換える。

## 7. 人間による失効・再発行チェックリスト

Git履歴に残る2種類の `APP_KEY` は公開済みとして扱う。値そのものをIssue、Pull Request、ログ、コミットメッセージへ転記せず、安全な環境で次を実施する。本番キーとの照合は人間による作業であり、このPull Requestでは照合、Git履歴の書き換え、本番キーの変更、秘密情報の失効・再発行を実施しない。

- [ ] 本番XServerの `APP_KEY` が、Git履歴に残る2種類のいずれかと一致するか確認する
- [ ] 一致する場合は、保守時間を確保して新しい `APP_KEY` を生成し、本番 `.env` を更新する
- [ ] `APP_KEY` 変更により、既存セッション、Cookie、Laravelで暗号化した保存値が復号できなくなる影響を確認する
- [ ] 設定キャッシュを再生成し、ログイン、Googleコールバック、主要APIを確認する
- [ ] 旧キーをバックアップ、ログ、共有メモから削除する
- [ ] Google Cloud Consoleで、リポジトリのプレースホルダー以外に漏洩したOAuthクライアントシークレットまたはAPIキーがないことを確認する
- [ ] 漏洩が確認されたGoogle認証情報がある場合は失効・再発行し、本番 `.env` を更新する
- [ ] GitHub Actionsの `ID_RSA` と `SLACK_WEBHOOK_URL` がIssue、ログ、外部共有先へ露出していないことを確認する
- [ ] 露出が確認されたActions Secretは提供元で失効・再発行し、GitHubの登録値を更新する
- [ ] 必要な場合は、関係者と履歴書き換えおよび全cloneの再取得手順を調整する

## 8. Issue #209を閉じる条件

Issue #209は、このPull Requestのマージだけでは閉じない。運用者が安全な環境で本番XServerの `APP_KEY` とGit履歴上の2種類を照合し、値を一切記録せず、一致または不一致という照合結果だけをIssue #209で確認できる状態になってから閉じる。

照合結果が一致の場合に必要となる本番キーの変更、影響確認、秘密情報の失効・再発行、Git履歴の書き換えは、このPull Requestの対象外とする。実施要否と手順は、照合結果に基づいて運用者が別途判断する。

## 9. 確認手順

秘密情報を検索する際は、必ず検出値を完全にマスクする。検索結果にはファイル名、コミット、キー名だけを残し、値を標準出力やレポートへ含めない。

Pull Requestでは次を確認する。

1. `.env`、秘密鍵、認証JSONが追跡対象に追加されていないこと
2. `.env.example` に本番値が含まれていないこと
3. Git差分に秘密情報形式の値がないこと
4. ローカル・テスト用設定だけでアプリケーションテストを実行できること
5. ApacheアクセスログにURLクエリが記録されないこと
6. MySQL general logが無効であること
