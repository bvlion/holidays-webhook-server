# ロールバック手順

この文書は、Issue #224に基づき、本番デプロイ後に問題が起きた場合の切り戻し条件と手順を整理したものである。前提となるデプロイ方式・バックアップ方針は [`deployment.md`](deployment.md) を参照する。実施はすべて人間（運用者）が行い、AIエージェントは本番へのSSH・DB接続を行わない（役割分担は[`deployment.md`](deployment.md) 1節）。

## 1. 基本方針

- **アプリケーションファイルだけ戻せば解決するケース**と、**DB restoreまで必要になるケース**を明確に分ける。DB restoreは破壊的操作であり、必要性を確認してから実施する。
- ロールバックの土台は、deploy前に取得した「直前リリースのアプリケーションファイルの控え」（[`deployment.md`](deployment.md) 5節）と、必要な場合の「DBバックアップ」（同8節）である。控えがない場合は、直前のtagのソースからComposer installし直す形になり、復旧に時間がかかる点に注意する。
- **`.env`・本番秘密情報を旧リリースファイルで上書きしない。** 現在のdeploy／ロールバックいずれの操作でも、配備先の`.env`はrsyncの対象外であり触れない設計にする（[`deployment.md`](deployment.md) 2節）。旧リリースの控えに`.env`が含まれていても、ロールバック時に上書き元として使わない。
- ロールバックを実施したら、[`deployment-checklist.md`](deployment-checklist.md)の「作業記録」に沿って、判断理由・実施内容・結果を記録する。

## 2. ロールバック要否の判断フロー

1. 問題を検知する（2節以降の各条件を参照）。
2. 直近のdeploy（tag push）が原因かどうかを切り分ける。deploy直後に発生し、直前は問題がなかった場合は、まずdeployが原因である可能性を優先して調べる。
3. 3節の表に沿って、アプリケーションファイルのみの切り戻しで足りるか、DB restoreまで必要かを判定する。
4. 4節（アプリファイルの切り戻し）または5節（DB restore）の手順を実施する。
5. 切り戻し後、[`deployment-checklist.md`](deployment-checklist.md)の「主要機能確認」相当の項目を再確認する。

## 3. 開始条件ごとの切り戻し方針

| 開始条件 | 主な切り分け観点 | 切り戻し方針 |
| --- | --- | --- |
| アプリケーションが起動しない（500エラー、白画面、公開URLが応答しない等） | rsync転送が途中で終わっていないか（[`deployment.md`](deployment.md) 2.2節のリスク）、`.env`が意図せず変わっていないか、必要なPHP拡張が揃っているか | 通常はアプリケーションファイルの切り戻し（4節）で復旧する。ファイル破損の疑いがあるときは切り戻し後に`vendor`を含めて再配置する。 |
| HTTP/APIの主要確認が失敗する（[`deployment-checklist.md`](deployment-checklist.md)の主要機能確認相当のエンドポイントがエラーになる） | 新リリースのコード起因か、DB接続・schema起因か | schema変更を伴わないリリースはアプリケーションファイルの切り戻し（4節）。schema変更を伴うリリースは6節を参照。 |
| Google連携が失敗する（`/auth/redirect`、`/login/callback`、休日情報取得） | Google側の一時的な障害か、コード変更・設定変更起因か。Google Calendar APIキー・OAuthクライアント設定は`.env`側にあり、rsyncでは変更されない（[`deployment.md`](deployment.md) 2節） | Google側要因なら切り戻し不要。コード変更が原因と判断できる場合はアプリケーションファイルの切り戻し（4節）。 |
| 外部HTTP実行が失敗する（コマンド実行・時間トリガー） | 実行先エンドポイント側の問題か、Guzzle呼び出しロジックの変更起因か | 呼び出しロジックの変更が原因と判断できる場合はアプリケーションファイルの切り戻し（4節）。実行先側の問題であれば切り戻し対象外。 |
| Laravel/PHPの例外やwarningが発生する | ログ（`logs/`、配備先で保持される。[`deployment.md`](deployment.md) 2節）の発生時刻とdeploy時刻を突き合わせる。schemaに関する例外（カラム不一致等）かどうかを確認する | コード起因であればアプリケーションファイルの切り戻し（4節）。DBスキーマ不一致が疑われる場合は6節を参照。 |
| schema変更を伴うリリースで問題が起きる | 6節を参照 | 6節を参照（DB restoreが必要になり得る） |

## 4. アプリケーションファイルのみの切り戻し

schema変更を伴わないリリースで、コード側の問題と判断できる場合に行う。DBには触れない。

1. 直前のリリースに対応するtag／commitと、deploy前に取得したアプリケーションファイルの控え（[`deployment.md`](deployment.md) 5節）を確認する。
2. 控えがある場合は、それを配備先へ復元する。控えがない場合は、直前のtagのソースを取得し、本番向けComposer install（`--no-dev`、[`deployment.md`](deployment.md) 6.1節）をやり直してから配備する。
3. 復元時も配備先の`.env`・`logs`には触れない。誤って上書きしないよう、復元元に`.env`が含まれる場合は事前に除外する。
4. 復元後、[`deployment.md`](deployment.md) 6.2節の順序（config:clear → route:clear/view:clear → cache:clear → 必要なら再cache）でLaravel cacheを再構築する。新リリースのキャッシュが残ったままだと、ファイルを戻しても古い挙動に戻らないことがある。
5. [`deployment-checklist.md`](deployment-checklist.md)の主要機能確認相当の項目で復旧を確認する。

## 5. DB restoreが必要になるケース

DB restoreは、直前のバックアップ以降に書き込まれたデータ（コマンド実行結果、ユーザー登録、休日キャッシュ登録等）を失う可能性がある破壊的操作である。**アプリケーションファイルの切り戻しだけで解決する問題に対して、安易にDB restoreを行わない。**

DB restoreを検討するのは、次のいずれかに該当する場合に限る。

- schema変更を適用した後にアプリケーションが正しく動作せず、かつアプリケーションファイルを直前リリースへ戻しても、DBのschemaが新しいままでは動作しない（6節）。
- schema変更を伴わないはずのリリースで、意図しないデータ破損・不整合がDB側に生じたことが確認できた場合。

実施する場合は、次の手順を踏む。

1. **DB restoreを実施する前に、現状のDBの状態を新たにバックアップする。** 復元自体が失敗した場合や、判断が誤っていた場合に、現状へ戻れるようにするため。
2. 復元に使うバックアップファイルが、意図した時点（直前リリース適用前）のものであることをファイル名・取得日時で確認する。
3. 次のいずれかの復元経路を、人間が状況に応じて選択する（[`deployment.md`](deployment.md) 8.1節）。
   - **XServerサーバーパネルから復元する**: XServer側の自動バックアップからの復元操作を使う。この経路は、手動でダウンロードしたSQLファイルを指定する方式ではない。
   - **Sequel Aceの`File → Import...`から復元する**: 既存のSSHトンネル経由で本番DBへ接続したSequel Aceで、手動取得したSQLファイルをImportする。gzファイルを直接Importできるかは未確認のため、必要に応じて非圧縮SQL側を使う。

   いずれの経路も実際のrestoreテストは今回行っておらず、復元操作・復元経路の存在を確認した段階である。
4. 復元後、アプリケーションファイルも復元先のschemaに対応するリリース（通常は直前リリース）に揃っているか確認する。アプリケーションのコードとDBスキーマの組み合わせがずれると、別の不整合を生む。
5. `.env`の接続情報（`DB_HOST`・`DB_DATABASE`等）を変更する必要はない前提だが、変更した場合は復元先のDBと一致しているか確認する。

## 6. schema変更を伴うリリースで問題が起きる場合

[`deployment.md`](deployment.md) 7.2節のとおり、schema変更を伴うリリースは対象のIssue/PRで適用手順・ロールバック手順を個別に明示する運用とする。本文書では、その個別手順を作成する際に踏まえるべき最低限の分岐だけを示す。

1. **schema変更をまだ適用していない、またはアプリケーションファイルの配備前に問題が判明した場合**: schema適用を行わず、アプリケーションファイルの配備も見送るか、4節の要領で直前リリースのファイルに留める。DBは変更されていないため、DB restoreは不要。
2. **schema変更を適用済みで、アプリケーションが新schemaを前提に動いている場合**: アプリケーションファイルだけを直前リリースへ戻すと、新schemaと旧コードの不整合で別の障害を起こす可能性がある。この場合は次のいずれかを選ぶ。
   - 新schemaのまま、コードだけ緊急修正して再deployする（schemaが後方互換な変更である場合に選びやすい）。
   - schema変更前の状態までDB restoreし、アプリケーションファイルも直前リリースへ戻す（5節の手順に従う。データ欠落のリスクを許容できるか、対象Issueの担当者・運用者が判断する）。
3. どちらを選ぶかは、対象リリースのIssue/PRに明示された想定影響範囲と、実際に発生した問題の内容を踏まえて人間が判断する。本文書は判断基準の型を示すものであり、個別リリースの具体的な適用・ロールバック手順の代わりにはならない。
